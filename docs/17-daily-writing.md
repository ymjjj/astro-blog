# 日常写作：自动保存、找回编辑与修改历史

双击项目根目录的 `start-studio.cmd`，打开终端显示的地址（默认 <http://127.0.0.1:4323>）。公开博客依然是静态文件；以下能力只在本地工作台、CLI 和 MCP 中运行。

## 自动保存与误关恢复

1. 在编辑器输入，停止输入约 1.8 秒后自动保存。新内容默认是草稿。已有发布内容也只修改本地文件，不自动提交、推送或上线。
2. 标题、摘要或正文尚未填完整时，保留为**恢复副本**，不会创建不合规的正式文章。顶部会显示“未填完整 · 恢复副本已保存”。
3. 关闭页面后重新打开，在“找回未完成的编辑”中点击“恢复编辑”。浏览器会即时保存表单；防抖到期后另存本机 `.blog/recovery`。后者可由同一项目的 CLI/MCP 或其他浏览器读取。
4. 恢复会建立新的编辑会话。原副本保留，确认找回并保存后可以“预览清理”。审查确认后副本移入回收站，不删除文章、历史版本或图片；可在回收站撤销。不要清理其他窗口仍在使用的副本。完整流程见 [恢复中心指南](19-maintenance-guide.md)。

浏览器副本属于当前浏览器、端口和项目。清除浏览器数据可能丢失尚未同步的文字；浏览器配额不足会提示。恢复副本不是异地备份，建议定期备份项目的内容、图片及 `.blog` 目录到你自己的存储位置。

### 当 Hermes 或其他窗口修改了同一篇内容

工作台保存时携带最后读取的 revision。磁盘内容已变化时显示冲突，停止自动写入，保留编辑器文字及恢复副本。

- 点击“读取磁盘版本”，查看最新正文和元数据。
- 在上方编辑器手动合并需要保留的内容，点击“已比较，使用合并后的编辑继续”。系统以刚才展示的磁盘版本为基准保存；若它又变化，仍会拒绝覆盖。
- 或点击“放弃编辑，使用磁盘版本”。这需要确认，并重新读取磁盘。

不要仅为了消除冲突而机械地换成最新 revision。revision 表示你已经检查过的版本。

### 保存中继续输入、网络中断

自动保存允许继续打字；响应返回时只更新已保存版本的信息，不用旧正文替换新输入。后续输入会进入下一轮保存。手动导图、预览等操作会等待正在进行的自动保存结束。

工作台在请求发出前缓存准确的 requestId 和参数。创建已经成功但响应丢失时，恢复后重试同一个请求，避免重复创建。错误后会保留编辑，检查状态后重试；不会无限轮询。长时间无响应会超时，超时本身不代表服务器没有执行。

## 粘贴与拖入图片

先保存一篇草稿，再使用任意入口：

- 文件选择器“插入图片”。
- 在 Markdown 正文框粘贴剪贴板中的图片。
- 把一张或多张图片拖到正文框。

三种入口都通过共用的 `image` 操作导入。逐张填写替代文本；取消某一张会跳过它。支持 JPEG、PNG、WebP、GIF、AVIF，每张不超过 10 MB，GIF 取第一帧。图片转为最大边 1800px 的 WebP，按内容哈希保存到 `src/assets/uploads`，引用插入正文的当前光标位置，然后进入自动保存。

只粘贴图片网址或 HTML 富文本不会自动下载远程图片。某张图片失败时，已插入的图片会保留，错误会显示；可继续处理剩余图片。图片二进制不塞进浏览器恢复表单，表单保存的是 Markdown 引用。

## 查看、比较与恢复历史

保存内容后点击“查看历史”，选择一个版本，再点击“与当前版本比较”。

- 顶部显示标题、摘要、日期、标签等字段的前后值。
- 正文中 `−` 表示旧版本中被移除的行，`+` 表示当前版本新增的行；没有标记的行未改变。
- 比较方向是“选中的旧版本 → 当前磁盘版本”。未保存的编辑不包含在这个对比中，请先保存。
- 确认恢复后，旧正文和元数据写入本地，**保留当前草稿/发布状态**。这不会发布，也不会撤回线上内容。
- 恢复前的内容会保留，可再次比较并恢复回来。历史图片不存在时拒绝恢复，先从备份找回图片文件。

历史按源文件哈希去重，记录版本内容，不是每次点击的操作流水。重复保存相同内容不增加版本；恢复到已存在版本会复用该版本记录。版本时间是首次记录时间，不一定是最近一次恢复时间。

经工作台、CLI、MCP 保存的修改会留下历史。首次修改已有文件时，也保留修改前的源文件。外部编辑器绕过接口产生的每次中间修改不会被自动追踪；下一次接口保存前会保留当时的磁盘版本。

## CLI 与 MCP 新接口

CLI 始终输出单个 JSON 对象。命令示例：

```powershell
node tools/blog/cli.mjs history --input request.json --json
```

`request.json` 可以用 UTF-8（带或不带 BOM）保存。下表中的哈希须取真实返回值，requestId 每次新操作使用新 UUID；重试相同请求则保留原 ID 和全部参数。

| CLI 操作 / MCP 工具              | 输入                                                  | 行为                                             |
| -------------------------------- | ----------------------------------------------------- | ------------------------------------------------ |
| `autosave` / `blog_autosave`     | `id, expectedRevision, requestId, body`，可选内容字段 | 与 update 相同的校验与冲突保护，已有内容自动保存 |
| `history` / `blog_history`       | `id`                                                  | 返回 currentRevision 及版本摘要                  |
| `diff` / `blog_diff`             | `id, fromRevision`，可选 `toRevision`                 | 不传 toRevision 时与当前磁盘版本比较             |
| `restore` / `blog_restore`       | `id, revision, expectedRevision, requestId`           | 恢复指定版本，保留发布状态                       |
| `recovery` / `blog_recovery`     | `{}` 或 `sessionId`                                   | 列出或读取恢复副本                               |
| `checkpoint` / `blog_checkpoint` | 见下例                                                | 保存可不完整的编辑表单，不改正式内容             |
| `discard` / `blog_discard`       | `sessionId, expectedVersion, requestId`               | 按版本清理恢复副本                               |

自动保存已有内容（使用真实的 revision 替换占位文字）：

```json
{
  "id": "posts/my-note",
  "expectedRevision": "从 read 返回的 64 位哈希",
  "requestId": "为本次操作生成的UUID",
  "body": "## 今天的笔记\n\n继续整理。"
}
```

创建不完整的恢复副本：

```json
{
  "sessionId": "4337de48-8aa9-4897-9ffb-48624c68cf07",
  "expectedVersion": null,
  "requestId": "70683811-af74-44e1-a5f9-bcaefc8dffb1",
  "id": null,
  "baseRevision": null,
  "form": {
    "kind": "posts",
    "slug": "",
    "title": "还没写完",
    "description": "",
    "date": "2026-09-27T12:00",
    "updated": "",
    "tags": "学习笔记，日常",
    "body": ""
  }
}
```

更新该副本时，expectedVersion 使用前次 checkpoint/recovery 返回的 version。已有文章的副本同时提供 `id` 和最近检查过的 `baseRevision`，form.kind 必须与 id 类型一致。form 中的日期与标签是原始表单字符串；不完整数据不会通过正式文章的校验。

Hermes 恢复历史的推荐顺序：

1. `blog_read` → `blog_history` → `blog_diff`，把要恢复的内容变化解释给用户。
2. 在用户要求恢复的范围内调用 `blog_restore`，`revision=diff.fromRevision`，`expectedRevision=diff.toRevision`。
3. `blog_check` / `blog_preview`，明确汇报“已恢复到本地”，不得声称已上线。
4. 遇到 REVISION_CONFLICT 重新比较合并；不要自动更换 expectedRevision 后覆盖。

未完成的长任务可调用 checkpoint。恢复时先读 recovery，若有 id 则再 read 比较 baseRevision；有差异先合并。确认不需要副本时再 discard。Hermes 具体主机版本仍需按安装环境接入；通用 stdio MCP 和 CLI 已实现。

## 实现原理与排错

内容核心位于 `tools/blog/core.mjs`；`history.mjs` 处理版本快照、逐行差异与恢复副本，`contracts.mjs` 定义三种入口共用的参数规则。`.blog` 已加入 Git 忽略，Astro 不读取它，工作台 HTTP 服务也不直接公开这个目录。

保存流程：校验参数 → 幂等请求记录与项目写锁 → 检查 revision → 检查图片与字段 → 保留旧源文件 → 再检查 revision → 原子替换 → 记录新版本。版本文件使用 SHA-256 校验；差异算法对大文档采用有上限的计算，大规模不同片段退化为整段替换，避免无界的二维数组。

浏览器按项目指纹与随机编辑会话隔离恢复副本。checkpoint/discard 使用独立 version 进行并发检查；发现副本冲突时工作台另建副本，保留原副本。编辑序号区分请求发出前后输入，防止迟到响应覆盖后续文字。

| 提示                       | 处理方法                                                             |
| -------------------------- | -------------------------------------------------------------------- |
| REVISION_CONFLICT          | 读取磁盘版本，检查双方修改，合并后保存                               |
| RECOVERY_CONFLICT          | 刷新恢复列表，检查最新副本；CLI/MCP 可另建 sessionId 保留双方        |
| VERSION_NOT_FOUND          | 重新读取 history，核对内容 ID；历史只存在本机 .blog 中               |
| HISTORY_CORRUPT            | 停止恢复，从可信备份找回版本文件，不手工篡改哈希绕过校验             |
| MISSING_IMAGE              | 从备份补回源图片，再进行保存或恢复                                   |
| 浏览器副本未保存           | 检查浏览器存储限制，及时手动保存；不要清空唯一的未保存副本           |
| BUSY / REQUEST_INTERRUPTED | 先确认正在执行的任务及源文件结果，遵循原写作指南恢复，不盲目重复创建 |

限制：项目写锁协调本工具的入口，无法锁住不遵守协议的外部编辑器；虽然替换前再次检查 revision，外部程序在最后检查与文件替换之间强行写入仍存在极短竞争窗口。需要强一致协作时让 Hermes 使用 CLI/MCP，避免第三方程序同时直接写同一文件。版本与副本当前不自动裁剪，避免未经确认丢失历史；长期使用应按空间情况备份和清理。

验证记录与后续状态见 [本轮进度](16-writing-progress.md)。基础发布与接入配置见 [原写作指南](13-writing-and-agents.md)。
